# Building NOOP

NOOP is an **offline-first** companion app for WHOOP straps (4.0 and 5.0/MG). It pairs
directly with the strap over Bluetooth Low Energy, stores everything on-device in SQLite, imports
WHOOP CSV exports and Apple Health exports, and computes recovery / strain / HRV / sleep locally.
There is no NOOP cloud or account. Optional, explicit network paths are documented in
[`PRIVACY_SECURITY.md`](PRIVACY_SECURITY.md).

> **Not affiliated with WHOOP, and not a medical device.** "WHOOP" is used only to identify the
> hardware this software interoperates with. NOOP contains no WHOOP code, firmware, or assets. All
> outputs (HR, HRV, recovery, strain, sleep, SpO₂, temperature) are approximations and are **not**
> clinically validated. See [`DISCLAIMER.md`](../DISCLAIMER.md) and [`ATTRIBUTION.md`](../ATTRIBUTION.md).

## Repository layout

The codebase is split into reusable Swift packages plus Apple app targets and an Android app. The
**macOS app is the reference implementation**; iOS/iPadOS ships as an unsigned IPA and as the `NOOPiOS`
Xcode target; the optional Watch companion ships inside the Full IPA. The Android app under `android/`
is a Kotlin shell (Bluetooth, Android services, Compose screens) around the same Swift core, compiled
for Android from `Packages/NoopCoreJNI`; it is in testing (see [Android](#android) below).
[`ARCHITECTURE.md`](ARCHITECTURE.md#2-repository-layout) describes the folders in more detail.


### Swift package tests on Linux

Install Swift 6 or newer plus a C compiler, `curl`, and `unzip`. GRDB uses SQLite's snapshot API,
which distribution builds commonly omit, so build a private snapshot-enabled library:

```bash
SQLITE_SNAPSHOT_DIR="$(mktemp -d)"
curl -fsSLo "$SQLITE_SNAPSHOT_DIR/sqlite.zip" https://sqlite.org/2026/sqlite-amalgamation-3530400.zip
unzip -p "$SQLITE_SNAPSHOT_DIR/sqlite.zip" sqlite-amalgamation-3530400/sqlite3.c > "$SQLITE_SNAPSHOT_DIR/sqlite3.c"
unzip -p "$SQLITE_SNAPSHOT_DIR/sqlite.zip" sqlite-amalgamation-3530400/sqlite3.h > "$SQLITE_SNAPSHOT_DIR/sqlite3.h"
echo "b1dd5d74ec7f29055a6684fa06fb3c2f6821c87dd38f9a458dfd2e8a1db28189  $SQLITE_SNAPSHOT_DIR/sqlite3.c" | sha256sum --check
cc -shared -fPIC -DSQLITE_ENABLE_SNAPSHOT=1 "$SQLITE_SNAPSHOT_DIR/sqlite3.c" -o "$SQLITE_SNAPSHOT_DIR/libsqlite3.so.0"
ln -s libsqlite3.so.0 "$SQLITE_SNAPSHOT_DIR/libsqlite3.so"
cd Packages/StrandAnalytics
LD_LIBRARY_PATH="$SQLITE_SNAPSHOT_DIR${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}" \
  swift test -Xcc -I"$SQLITE_SNAPSHOT_DIR" -Xlinker -L"$SQLITE_SNAPSHOT_DIR"
```

This currently runs 1,523 platform-neutral package tests with one intentional skip. It does not run
iOS simulator/UI tests or Darwin's Compression-backed raw outbox. The existing package CI remains
macOS-only.

The same two flags work for the other GRDB-linked packages — swap the `cd` and repeat:

| Package | Linux status |
|---|---|
| `StrandAnalytics` | builds + tests (1,523, one skip) |
| `WhoopStore` | builds + tests (439) |
| `StrandImport` | builds + tests (249, one skip) |
| `NoopLocalAccess` | builds + tests (9) |
| `StrandDesign` | macOS only (SwiftUI) |

The Compression-backed raw outbox is Darwin-only, so the tests that drive it (`RawOutboxTests`,
`PruneTests`, and the raw half of `ReadTests.testStorageStats`) compile out off Darwin. Everything they
cover still runs in the macOS CI job.

Because none of this runs in CI, treat a green Linux run as a convenience rather than a guarantee.

## macOS build & run (reference implementation)

The macOS project is **generated**, not committed by hand. `project.yml` is the source of truth;
`Strand.xcodeproj` is produced from it. Re-run generation whenever you add/remove source files or
change `project.yml`.

### 1. Generate the Xcode project

```bash
cd /path/to/noop_forge
xcodegen generate
```

### 2. Build

```bash
xcodebuild \
  -project Strand.xcodeproj \
  -scheme Strand \
  -destination 'platform=macOS' \
  CODE_SIGNING_ALLOWED=NO \
  build
```

Notes on the build:

- The Xcode **scheme is `Strand`** (the target is still named `Strand` internally). `project.yml` sets
  `PRODUCT_NAME: "NOOP Staging"`, so the built bundle is **`NOOP Staging.app`**, with display name
  `NOOP Forge`, the Swift module name pinned to `Strand`, and bundle id `$(BUNDLE_ID_PREFIX).noop.staging`
  (`com.noopapp.noop.staging` unless `Config/BundleIdSecrets.xcconfig` sets another prefix). This
  identity installs beside the official app with separate data.
- `CODE_SIGNING_ALLOWED=NO` skips signing for a fast local compile-and-verify loop. To produce a
  runnable `.app` you instead want an **ad-hoc-signed** build (see below).
- SPM resolves `GRDB.swift`, `ZIPFoundation`, `swift-crypto` and `MarkdownUI` on first build.

### 3. The ad-hoc-signed app

The app is **sandboxed** and requests Bluetooth, user-selected-file and outbound network-client access
(the opt-in Coach and the exercise-library source use the latter). `project.yml` declares these
entitlements and generates `Strand/Resources/Strand.entitlements` from them; the three core keys are:

```xml
<key>com.apple.security.app-sandbox</key>            <true/>
<key>com.apple.security.device.bluetooth</key>       <true/>
<key>com.apple.security.files.user-selected.read-write</key> <true/>
```

`project.yml` deliberately keeps `DEVELOPMENT_TEAM` empty and uses **ad-hoc signing** — no Apple Developer
account is required to run a personal build. To produce the
runnable bundle, build without disabling signing so Xcode applies the sandbox + Bluetooth
entitlements with an ad-hoc identity:

```bash
xcodebuild \
  -project Strand.xcodeproj \
  -scheme Strand \
  -configuration Debug \
  -destination 'platform=macOS' \
  -derivedDataPath build \
  CODE_SIGN_IDENTITY="-" \
  build
```

The product lands at `build/Build/Products/Debug/NOOP Staging.app`. You can confirm it is ad-hoc signed:

```bash
codesign -dvv "build/Build/Products/Debug/NOOP Staging.app"
# Signature=adhoc
# Identifier=com.noopapp.noop.staging   (your BUNDLE_ID_PREFIX, if you set one)
# TeamIdentifier=not set
```

Copy the bundle wherever you like and double-click to launch. On first
run macOS prompts for Bluetooth permission — the prompt text comes from
`NSBluetoothAlwaysUsageDescription` in the Info.plist and explains that data stays on-device.

### 4. Pairing & BLE on macOS

NOOP connects over CoreBluetooth (`Strand/BLE/BLEManager.swift`). The central manager is created
on the main queue:

```swift
central = CBCentralManager(delegate: self, queue: .main)
```

so all delegate callbacks arrive on the main actor. WHOOP 4.0 uses the `61080001-…` service family
with a CRC8 header; WHOOP 5.0 (the "goose"/MG path) uses the `fd4b0001-…` family with a
CRC16-Modbus header. The strap must be **out of range of the official app** during initial bonding,
and worn/charged to report a non-zero heart rate.

### 5. Dev loop

```bash
# after editing project.yml or adding/removing files:
xcodegen generate

# fast syntax/type check (no signing, no bundle):
xcodebuild -project Strand.xcodeproj -scheme Strand \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build

# per-package iteration (much faster than the full app):
cd Packages/WhoopProtocol && swift build && swift test
cd Packages/WhoopStore    && swift build && swift test
cd Packages/StrandImport  && swift build && swift test
```

You can also open the generated project interactively:

```bash
open Strand.xcodeproj
```

### 6. Re-importing data into the on-device DB

The on-device SQLite database lives inside the app sandbox container (`<bundle id>` is the id from the
build notes above):

```
~/Library/Containers/<bundle id>/Data/.../whoop.sqlite
```

`Tools/Backfill` is a small executable that re-runs the WHOOP CSV / Apple Health import mapping
directly against that database — useful after changing importer logic:

```bash
cd Tools/Backfill
swift run backfill
```

## iOS (unsigned sideload release and source builds)

iOS ships as an **unsigned sideload release** plus a build-from-source target. There is **no App Store
or TestFlight build** — both require a real Apple Developer identity, which is fundamentally at odds
with NOOP staying anonymous. The release IPA carries no signing identity; AltStore or SideStore signs
it locally with the user's own Apple ID. See [IOS.md](IOS.md) for the source URL and install steps.
The iOS app uses the same store and analytics implementations as macOS. BLE requires a real iPhone;
the simulator is suitable only for UI and non-BLE work.

The `NOOPiOS` app target, the `NOOPiOSWidgets` WidgetKit / Live Activity extension, and the `NOOPWatch`
app with its `NOOPWatchComplications` extension already exist in `project.yml` — you don't need to add
them. Shared app code remains under `Strand/`; the iOS shell, Forge screens, HealthKit and widget
publishers live under `StrandiOS/`, the widgets under `StrandiOSWidgets/`, and the Watch sources under
`NOOPWatch/` and `NOOPWatchComplications/`.

### Build & run

`NOOPiOS` links the on-device embedding runtime, which is not committed. Fetch it **before** generating the
project, because XcodeGen enumerates `Vendor/Nomic/Resources` when it generates:

```bash
Tools/bootstrap-nomic.sh          # downloads llama.xcframework and the pinned embedding model, verifies checksums
Tools/bootstrap-nomic.sh --check  # only verifies that both are present
```

```bash
cd /path/to/noop_forge
xcodegen generate

# build for a connected iPhone (real device — BLE doesn't work in the simulator):
xcodebuild \
  -project Strand.xcodeproj \
  -scheme NOOPiOS \
  -destination 'generic/platform=iOS' \
  build
```

Or open the generated project and run the `NOOPiOS` scheme from Xcode:

```bash
open Strand.xcodeproj
```

Notes:

- The `NOOPiOS` and `NOOPiOSWidgets` targets deploy to **iOS 17.0** (`NOOPWatch` and its complications to
  watchOS 10.0). (The shared packages still
  declare a floor of iOS 16 — `.iOS(.v16)` — but the app targets require iOS 17.)
- Running on a physical iPhone needs a signing identity selected in Xcode (a free personal Apple ID
  works for on-device builds). **BLE requires a real device** — the iOS simulator can't reach a
  physical strap.
- The iOS app reuses `BLEManager` (CoreBluetooth is identical API on iOS) and the shared analytics,
  store, import, and design packages. `StrandDesign` already bridges `NSColor`/`UIColor` behind
  `#if canImport(AppKit) / #elseif canImport(UIKit)`, so the palette, fonts, and components carry
  over. `BUNDLE_ID_PREFIX` also feeds the App Group id and the Watch companion pairing, so a build under
  your own Apple ID needs `Config/BundleIdSecrets.xcconfig` (copy `Config/BundleIdSecrets.example.xcconfig`). macOS-only surfaces (the menu-bar HR extra, screen-lock / Shortcut strap actions) have no
  iOS equivalent and are `#if os(macOS)`-gated; iOS uses a widget / Live Activity instead.

## Release workflows

Four GitHub Actions workflows build what testers and users download. All are started by hand from the
Actions tab (`workflow_dispatch`); none runs on an ordinary push.

| Workflow | Produces | Notes |
|---|---|---|
| `publish-ios-release.yml` ("Publish unsigned iOS release") | The public release `v<VERSION>-dx`: two IPAs, a universal macOS zip, the Android APK, checksums and attestations | The release path. Input: the numeric version, already committed to `project.yml`. Dispatch from `main`. |
| `fork-release.yml` ("Release build (fork)") | A non-prerelease `v<VERSION>` release with a macOS zip and IPAs | Inputs: `bump` (patch, minor, major, none) and an optional explicit version. It commits the version bump to the dispatched branch. It does not build the Android APK and does not write checksum files or attestations. |
| `fork-testing-build.yml` ("Testing build (fork)") | The rolling prerelease `testing-latest` with `NOOP-testing-macos-v<VERSION>.zip`, the two `NOOP-testing-ios-…-v<VERSION>.ipa` files and `NOOP-testing-android-v<VERSION>.apk` | Input: a one or two sentence summary. Recreates the single `testing-latest` release on every run, so a failed leg leaves it without that artifact. |
| `android-release.yml` ("Android release APK") | The signed APK attached to a release (`NOOP-Forge-android-<VERSION>-testing.apk`, or `NOOP-testing-android-v<VERSION>.apk` for the testing channel) | Called by the two workflows above after the release exists; can be run by hand (`dry_run` builds and checks the signature only, `tag` attaches to an existing release). Needs the release keystore secrets. |

### Publish an unsigned Apple release

The **Publish unsigned iOS release** workflow is intentionally manual. Before it is dispatched from `main`,
commit the numeric version and monotonic build number in `project.yml`, add the matching release note at
`docs/fork/releases/v<VERSION>.md`, and run `Tools/appchangelog-gen.py` on that note so the in-app
“What's New” card matches the release.

The workflow first waits for `swift-packages.yml`, validates its inputs, fetches the pinned embedding
runtime and model (`Tools/bootstrap-nomic.sh`), builds `NOOPiOS` without a signing identity and packages
two artifacts:

- `NOOP-ios-unsigned-v<VERSION>-dx.ipa` retains the iOS widget and removes only the embedded Watch app.
  The sideload preparation step leaves AltSign a capability template for the shared App Group and
  HealthKit, so the widget can show the installed app's real data.
- `NOOP-ios-full-unsigned-v<VERSION>-dx.ipa` retains the widget, Watch app and Watch complication for
  people who can provision the complete bundle with their own developer team.

The release is created as a prerelease while those assets build. A separate macOS job attaches a
universal, ad-hoc-signed `NOOP-macos-v<VERSION>-dx.zip`, and the Android job attaches the signed APK;
only after both Apple platforms succeed does the final job promote `v<VERSION>-dx` to the latest public
release. The publishing job also prepends the actual IPA URL and size to `altstore-source.json` and
commits that manifest-only change to `main`.

The workflow needs repository Actions permissions set to **Read and write** and permission for the
GitHub Actions bot to push its manifest-only commit to `main`. It never receives an Apple certificate,
provisioning profile, or personal developer name. The Android job uses the release keystore from
repository secrets.

### Checksums and build provenance

Release and testing builds attach a SHA-256 file next to their artifacts
(`NOOP-ios-v<VERSION>-dx.sha256`, `NOOP-macos-v<VERSION>-dx.sha256`, the APK's `.sha256`; the testing
build names them `NOOP-testing-…-v<VERSION>.sha256`). Each attached file also receives a signed GitHub
build provenance attestation (`actions/attest-build-provenance`) that ties it to this repository, the commit
and the workflow run. To check a download:

```bash
shasum -a 256 -c NOOP-ios-v<VERSION>-dx.sha256            # in the folder with the files
gh attestation verify <file> --repo DX23876/noop_forge
```

The attestations come from `publish-ios-release.yml`, `fork-testing-build.yml` and `android-release.yml`
(which request `id-token` and `attestations` write permission); `fork-release.yml` does not produce them.

## Android

The Android app (`android/`, applicationId `io.github.dx23876.noop`, Android 8.0+ / minSdk 26) is in
testing (see [`fork/android/TESTING.md`](fork/android/TESTING.md) and
[`fork/android/STATUS.md`](fork/android/STATUS.md)). Its store and its scoring are the shared Swift
core's; Kotlin keeps Bluetooth, Android services and the screens. Every build compiles the shared Swift
core from `Packages/NoopCoreJNI` into `libNoopCore.so` (arm64) and packs it with the Swift runtime into the
APK. The `versionName` is read from `MARKETING_VERSION` in `project.yml`.

Prerequisites, as pinned in `.github/workflows/android.yml` and `android/swift-core/build-swift-core.sh`:

| Tool | Version | Notes |
|---|---|---|
| JDK | 17 | `jvmTarget` in `android/app/build.gradle.kts` |
| Gradle | 8.7 | provisioned by `android/gradlew`; no system Gradle needed |
| Android SDK | `compileSdk` 35 | via `$ANDROID_HOME` or `android/local.properties` (`sdk.dir=…`) |
| Android NDK | r30 (`30.0.16248370`) | `$ANDROID_NDK_HOME`, or `$ANDROID_HOME/ndk/30.0.16248370` |
| Swift toolchain | 6.4.1 (swift.org) | must match the Swift SDK; on macOS the script looks under `~/Library/Developer/Toolchains`, `NOOP_SWIFT` overrides it |
| Swift SDK for Android | `swift-6.4.1-RELEASE_android` | `swift sdk install <artifactbundle>`, then its `setup-android-sdk.sh` |

The app has no Room entities, DAOs or migrations: its data access is `com.noop.data.CoreWhoopDao`,
generated from the annotated DAO declarations by `Tools/gen_core_dao.py`, and every statement runs in the
core's GRDB database. After editing `WhoopDao.kt`, `DeviceRegistryDao.kt` or the entity classes, run
`python3 Tools/gen_core_dao.py` to rewrite it (`--check` fails when it is out of date). Room stays only as a
transitive dependency of WorkManager.

The Gradle task `buildSwiftCore` runs `android/swift-core/build-swift-core.sh` before every build. The
script downloads and checks the same snapshot-enabled SQLite amalgamation as the Linux package build
above, patches GRDB and ZIPFoundation for Android (`patch_dependencies.py`) and copies every shared
library `libNoopCore.so` needs into the APK.

```bash
cd android
./gradlew assembleFullDebug assembleDemoDebug assembleFullDebugAndroidTest
python3 swift-core/check-apk-resources.py app/build/outputs/apk/full/debug/*.apk app/build/outputs/apk/demo/debug/*.apk
./gradlew testFullDebugUnitTest
```

These are the commands `android.yml` and `Tools/local-tests.sh` run (the latter for any change under
`android/`, `Packages/`, `project.yml` or `Tools/parity_cases/`). The unit tests include the parity
oracles in `android/app/src/test/resources/core_parity/`. `Full` is the real app; `Demo` installs beside it with a
DEMO badge so every screen can be explored without a strap.

A release APK is built and signed only by `.github/workflows/android-release.yml` (release key from
repository secrets), which the Apple release workflow calls after it has created the release; it
attaches `NOOP-Forge-android-<VERSION>-testing.apk`. No published release carries one yet.
